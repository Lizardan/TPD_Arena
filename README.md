# TPD Arena — Telegram-бот групповых боёв с GIF-записями

Всё-в-одном Cloudflare Worker (бесплатный тариф): бот (`/arena`) + детерминированная симуляция боя + рендер GIF без canvas/DOM (пиксельный буфер → gifenc).

## Как работает

1. В группе (или супергруппе) любой участник пишет `/arena` (или `/арена`, или жмёт нижнюю кнопку **«⚔️ Выйти на арену»**).
2. Бот присылает «⚔️ АРЕНА СОЗДАНА» со случайной статистикой (HP / сила / скорость) и одной кнопкой — **«⚔️ Выйти против @ник»** (зелёная).
3. Другой участник жмёт кнопку выхода → бот меняет текст на «🔥 ИДЁТ БОЙ!», рендерит GIF, удаляет сообщение и отправляет гифку в чат с подписью результата.
4. Любой участник может закрыть арену командой `/stop` — бой не начнётся, кнопка с карточки снимается.

Ограничения: бот не может принять собственный вызов; на чат одна активная арена (протухает через 10 минут); callback-кнопка одноразовая.

## Команды и кнопки

В меню команд Telegram у бота две команды — `/arena` и `/stop`.

| Элемент | Тип | Что делает |
|---|---|---|
| `/arena` (`/арена`) | команда | открыть арену в чате |
| `/stop` (`/стоп`) | команда | закрыть все арены в чате — может любой участник |
| «⚔️ Выйти на арену» | нижняя клавиатура (`ReplyKeyboardMarkup`, `is_persistent`) | присылает текст кнопки → бот воспринимает это как `/arena` |
| «⚔️ Выйти против @ник» | inline-кнопка на карточке, `style: 'success'` | принять вызов и запустить бой |

Карточка арены несёт **ровно одну** кнопку — призыв к действию. Закрытие арен вынесено в `/stop`, чтобы плашка не предлагала двух равнозначных путей.

Цвет кнопок (`style`: `primary` / `success` / `danger`) применяют клиенты Telegram, выпущенные после 9 февраля 2026 года; более старые показывают кнопки без заливки, но полностью рабочими. Иконки-эмодзи (`icon_custom_emoji_id`) не используются: они доступны только ботам с юзернеймом, купленным на Fragment, либо при Telegram Premium у владельца бота, — поэтому эмодзи стоят прямо в тексте кнопки.

**Почему нижняя клавиатура приходит отдельным сообщением.** У сообщения есть только одно поле `reply_markup`, и оно вмещает либо inline-клавиатуру, либо reply-клавиатуру — но не обе сразу. Карточке арены нужна inline-кнопка (она несёт `callback_data`), поэтому нижняя клавиатура едет отдельным коротким сообщением. Она `is_persistent` и `resize_keyboard`, то есть остаётся под полем ввода, пока пользователь сам её не спрячет, — поэтому бот ставит её **один раз на чат** (факт установки хранится в KV под ключом `menu:<chatId>`).

**Важно: privacy mode.** Кнопка нижней клавиатуры работает как обычное текстовое сообщение от пользователя. Если у бота включён Group Privacy, Telegram **не доставляет** боту обычные сообщения группы — значит, нажатие нижней кнопки бот не увидит. Чтобы кнопка работала, выключи privacy: [@BotFather](https://t.me/BotFather) → `/setprivacy` → выбрать бота → **Disable**. Команды (`/arena`, `/stop`) и inline-кнопки на карточке работают при любом режиме: privacy фильтрует только обычный текст. CI-шаг «Check group privacy mode» печатает предупреждение, если privacy всё ещё включён.

Меню команд бот ставит сам: `setMyCommands([{command: 'arena', …}, {command: 'stop', …}])`. Это делает CI при деплое, а воркер повторяет вызов один раз на изолят (`syncCommands`) — так меню остаётся верным, даже если его правили руками в BotFather.

## Анимация и рендер

Сцена рисуется в индексированный буфер (`Uint8Array`), без canvas и DOM.

**Спрайты.** Боец собирается из частей: задняя рука, две ноги с ботинками, таз,
кираса с бликом и эмблемой, пояс с пряжкой, наплечники, шея, голова со шлемом,
гребнем и лицом, передняя рука с оружием. Каждая часть обводится контуром, свет
падает сверху-слева. Оружие выбирается детерминированно по нику: меч, булава или
копьё.

**Машина состояний.** `dead > attack > hurt > idle`.
- `idle` — дыхание плюс медленный перенос веса на другом периоде (не «двухкадровый» цикл);
- `attack` — замах (отвод назад, подъём оружия) → удар (резкий выпад, замах вниз) → возврат, с easing;
- `hurt` — отдача назад и короткая вспышка;
- `dead` — падение с наклоном и лежачее тело с выпавшим оружием.

**Time-warp: клип как нарезка лучших моментов.** Раньше весь бой равномерно
сжимался в 2.5 с при 8 fps, из-за чего удар 0.35 с попадал ровно в один кадр —
отсюда «дёрганость». Простое «сжимать меньше» не работает: бой на 30 разменов
требует ~200 кадров только на удары, а бюджет — 36.

Поэтому таймлайн строится иначе:

1. каждый удар становится «дублем»; перекрывающиеся удары сливаются в один
   непрерывный дубль (не длиннее 1.2 с, чтобы затяжная свалка всё равно дала
   список, из которого можно выбирать);
2. из дублей выбираются те, что влезают в бюджет, **равномерно по всему бою** —
   первый размен и добивающий удар входят всегда, так что клип рассказывает всю
   историю, а не только начало;
3. каждый выбранный дубль играется в **полную длину** (не короче ~3.5 кадров) —
   именно это и даёт плавность;
4. время между дублями превращается в короткую паузу, причём пауза привязывается
   к моменту, когда **никто не атакует**: иначе невыбранные удары попадали в
   «паузу» и боец мигал позой атаки на двух кадрах. Если свободного момента нет
   (непрерывная свалка) — пауза просто убирается, и дубли идут встык.

Длительность анимации удара выводится из собственной скорости бойца
(`min(0.5 c, интервал × 0.7)`), поэтому быстрый боец не залипает в вечной позе
атаки. Равномерное сжатие осталось только как аварийный вариант для входов,
недостижимых через бота (999 HP при скорости 10 через `/render`).

**Эффекты.** Тряска экрана при попадании, искры, пыль из-под ног при выпаде,
всплывающие числа урона с обводкой, HP-бар с рамкой, делениями и белой полосой
недавно потерянного здоровья.

**HUD имён.** Плашка имени автоматически подбирает масштаб: сначала пробуется
крупный шрифт в одну строку, затем мелкий в одну строку, затем перенос на две
строки, и только потом обрезка. Плашка центрируется над бойцом, но зажимается в
свою половину кадра, поэтому два длинных ника никогда не наезжают друг на друга.

**Дельта-кадры GIF.** Фон арены статичен, поэтому в каждом кадре неизменные
пиксели пишутся как прозрачные (`dispose: 1`), и декодер оставляет то, что уже
есть. Файл выходит примерно вдвое меньше (≈47 КБ против ≈95 КБ полными кадрами) и
короче LZW-поток. Отключить можно через `encodeGif(..., { delta: false })` — тест
сверяет оба варианта, а `test/gif-decode.mjs` декодирует результат обратно и
проверяет попиксельное совпадение с исходными кадрами.

## Локальный запуск / тесты

```bash
npm install
npm test        # vitest (54 теста)

npm run bench   # сравнение профилей рендера + бюджет CPU (worst case по 40 боям)
npm run cost    # раскладка времени: рендер / патч / LZW, доля изменённых пикселей
npm run verify  # сквозная проверка: таблица состояний по кадрам, листы, round-trip GIF

node test/verify.mjs nicknames   # сценарии: realistic | grind | nicknames | frantic
node test/poses.mjs 6            # лист поз спрайта
node test/zoom.mjs 1 8 0,10,20,30   # увеличенные кадры боя
node test/gif-decode.mjs 1 5     # декод GIF + контактный лист
```

`npm run verify` печатает состояние каждого кадра (`i`/`a`/`h`/`d` для idle,
attack, hurt, dead) — по этой таблице видно, что паузы действительно паузы, а
удары идут в полную длину, без необходимости разглядывать гифку глазами.

Превью: открой `render/preview.html` через HTTP-сервер (ES-модули не работают с `file://`):

```bash
cd F:\Unity Projects\TPD_Arena
npx serve .        # или: python -m http.server
# http://localhost:3000/render/preview.html
# в адрес можно добавить ?battle=<base64url-json> для конкретного боя
```

## Деплой через GitHub Actions (рекомендуется)

Workflow `.github/workflows/deploy.yml` сам: прогоняет тесты → создаёт KV namespace (если нет) → ставит секреты → `wrangler deploy` → подключает Telegram webhook → ставит меню команд (`/arena`, `/stop`) → проверяет group privacy и предупреждает, если она включена.

**Нужно один раз:**

1. Создай репозиторий на GitHub (например `TPD_Arena`) и запуши код:
   ```bash
   git init -b main
   git add .
   git commit -m "TPD Arena: бот + GIF-рендер"
   git remote add origin https://github.com/<ваш_логин>/TPD_Arena.git
   git push -u origin main
   ```
2. В репозитории: `Settings → Secrets and variables → Actions` добавь секреты:
   | Секрет | Значение |
   |---|---|
   | `CF_API_TOKEN` | Cloudflare API-токен (правила: Workers Scripts Edit, Account Settings Read) |
   | `CLOUDFLARE_ACCOUNT_ID` | твой Account ID из дашборда Cloudflare |
   | `BOT_TOKEN` | токен бота из @BotFather (`8835068690:AAF7...`) |
   | `WEBHOOK_SECRET` | любая случайная строка (совпадёт с `secret_token` вебхука) |

   Пример `WEBHOOK_SECRET`: `l8ra28HRSw8e6QdRPSJT8jl8GeJ5d5KJ`.

3. Workflow стартует на `push` в `main`. Следи за `Actions` на GitHub.
4. Рабочий адрес бота: `https://tpd-arena-bot.<ACCOUNT_ID>.workers.dev/hook`. Проверь через `https://tpd-arena-bot.<ACCOUNT_ID>.workers.dev/health`.
5. Добавь бота в группу (включи права на удаление сообщений) и пиши `/arena`.

Ручной деплой тоже возможен — см. ниже.

## Ручной деплой

1. Создай бота у [@BotFather](https://t.me/BotFather). Там же: `/setprivacy` → выбрать бота → **Disable**, иначе бот не увидит нажатий нижней кнопки «⚔️ Выйти на арену» (inline-кнопки работают в любом случае).
2. Войди и создай KV namespace:

```bash
npx wrangler login
npx wrangler kv namespace create ARENAS
```

3. Вставь полученный `id` в `bot/wrangler.toml` (раскомментируй блок `kv_namespaces`).
4. Задай секреты:

```bash
npx wrangler secret put BOT_TOKEN
npx wrangler secret put WEBHOOK_SECRET
```

`WEBHOOK_SECRET` — любая случайная строка (бот проверяет заголовок `X-Telegram-Bot-Api-Secret-Token`).

5. Деплой:

```bash
npm run deploy
```

6. Привяжи вебхук (подставь свой URL и тот же secret):

```bash
npx wrangler secret put WEBHOOK_SECRET   # если ещё не задал
curl -s "https://api.telegram.org/bot<TOKEN>/deleteWebhook"
curl -s "https://api.telegram.org/bot<TOKEN>/setWebhook?url=https://<worker>.workers.dev/hook&secret_token=<WEBHOOK_SECRET>"
```

7. Поставь меню команд — `/arena` и `/stop`:

```bash
curl -s -X POST "https://api.telegram.org/bot<TOKEN>/setMyCommands" \
  -H 'Content-Type: application/json' \
  -d '{"commands":[{"command":"arena","description":"Выйти на арену"},{"command":"stop","description":"Офнуть все арены в чате"}]}'
```

Воркер повторит этот вызов сам при первом апдейте, так что шаг необязательный — он нужен, если хочется, чтобы меню было верным сразу.

8. В группу нужно добавить бота. Для удаления сообщений (атака!) у него должны быть права на удаление.

## Производительность (бесплатный тариф)

Профиль `FREE_PROFILE`: **136×102, 12 fps, до 36 кадров** (≈3 с GIF, 4 размена).

Худший случай по 40 боям, набранным **из собственных диапазонов бота**
(`rollStats`: HP 80–180, сила 6–26, скорость 0.6–1.8):

| Мера | Время |
|---|---|
| один прогретый запрос | **7.6 мс** |
| среднее под непрерывной нагрузкой | **9.3 мс** (рендер 3.5 / кодирование 5.9) |

Оба числа внутри лимита ~10 мс CPU на запрос Cloudflare Workers. Враждебные
входы, недостижимые через бота (999 HP при скорости 10 — только через `/render`),
дают 8.8 / 9.0 мс на 30 кадрах.

Замеры — `node test/sweep.mjs`. Скрипт печатает **две** цифры, потому что они
ограничивают истину с двух сторон: лучший одиночный прогрев (изолят уже прогрет,
куча в равновесии) и среднее по серии подряд (та же работа, но процесс ещё и
платит за аллокацию и сборку 36 буферов кадров на итерацию). Замер одиночных
вызовов *после принудительного GC* третьей точкой не является: полный GC
опустошает молодое поколение, и замер начинается с его повторного заполнения —
результат улетает втрое выше даже «нагрузочного».

**Куда уходит время.** Раскладка на реальных кадрах (`node test/cost.mjs`):

```
патч дельта-кадров   1.2 мс
LZW (gifenc)         4.6 мс
рендер кадров        ~2 мс
```

Ключевой момент: `gifenc` **обходит все пиксели каждого кадра**, независимо от
того, изменились они или нет. Дельта-кадры покупают размер файла и длину
LZW-потока, но не сокращают цикл по пикселям. Поэтому бюджет регулируется числом
кадров и площадью холста, а не сложностью сцены: ~0.25 мс на кадр при 136×102.
Отсюда же и главная оптимизация в `gif.js` — переиспользуемый патч-буфер, заранее
выделенный поток и `bytesView()` вместо копии: это не ускоряет LZW, но убирает
~130 КБ мусора на запрос.

Для сравнения, исходный профиль был 128×96, 8 fps, 20 кадров: в 1.8 раза меньше
кадров и в 1.5 раза ниже частота, из-за чего удар занимал один кадр.

**Если упрёшься в лимит** — `FREE_PROFILE.maxFrames` режет и рендер, и кодирование
почти линейно (~0.25 мс на кадр). Один лишний размен стоит ~6 кадров, то есть
~1.5 мс; на 36 кадрах помещается ровно 4 размена, на 48 — пять. Ещё есть
`holdAfter` (удержание финальной позы, 0.3 с): его уменьшение освобождает кадр под
размен. `fps` снижать не стоит — именно он убирает ощущение низкого FPS.

## Опционально: рендер по HTTP

`POST /render` принимает JSON боя и отдаёт `image/gif`:

```bash
curl -X POST https://<worker>.workers.dev/render \
  -H "Content-Type: application/json" \
  -d '{"left":{"name":"Иван","hp":100,"attackPower":12,"attackSpeed":1},"right":{"name":"Петя","hp":100,"attackPower":8,"attackSpeed":2}}' \
  -o battle.gif
```

При заданном `RENDER_KEY` в `[vars]` нужен заголовок `X-Render-Key` (в `wrangler.toml`).

## Формат JSON боя

```jsonc
{
  "left":  { "name": "имя (≤ 8 в HUD)", "hp": 80, "attackPower": 12, "attackSpeed": 1.0, "color": "#rrggbb" },
  "right": { ... },
  // hp: 1..999, attackPower: 1..999, attackSpeed: 0.1..10
  // color необязателен — выберется цвет по имени
}
```

Все поля валидируются; симуляция детерминирована (равные тайминги → первым левый).

## Маршруты

- `POST /hook` — вебхук Telegram (проверка `X-Telegram-Bot-Api-Secret-Token`)
- `POST /render` — рендер GIF по JSON (опц. авторизация `X-Render-Key`)
- `GET /health` — «ok»
